<objective>Hold the SVRT1 wire format in one module with the HMAC primitive as its only adapter, instead of three hand-synchronised implementations.</objective>

<blocked>
**Do not execute this plan on the strength of the architecture review.**

`CLAUDE.md` records a standing decision that the SVRT1 format is implemented three times
against three crypto APIs and that the three must stay byte-compatible. This plan reverses
that decision. It needs an explicit ruling first.

**The case for reopening:** `shared/protocol/socket.ts` already resolves from both the
Next.js build and the socket-server ESM build. The runtime constraint that motivated three
copies — "these builds cannot share a module" — is demonstrably not true in this repo.
What actually varies is one function: HMAC-SHA256 over a string. That is an adapter, not a
reason to triplicate a security-critical format.

**The case for leaving it alone:** three small copies with a byte-compatibility test are
comprehensible, and a shared module that must satisfy Convex's bundler, Node ESM, and the
Next.js server is a new failure mode on the room-admission path — the one path where a
subtle break locks every teacher and student out of every classroom.

**If the ruling is to keep three copies:** close this plan, and record the reasoning in
`CLAUDE.md` next to the existing decision so the next architecture review does not
re-propose it. That outcome is a legitimate result of this plan, not a failure of it.
</blocked>

<context>
Three implementations of one format:

- `convex/sessions.ts:63` `signSocketToken` — WebCrypto, the real production minting path
- `socket-server/src/server.ts:37` `mintRoomToken` / `:56` `verifyRoomToken` — `node:crypto`
- `lib/socket-token.ts` + `app/api/proof-socket-token/route.ts` — dev/proof minting, gated
  on `NODE_ENV === "development" && ALLOW_PROOF_SOCKET=1`

Only the third is genuinely optional. The first two are both load-bearing and must agree
on header, claim order, base64url padding, and signature encoding.
</context>

<tasks>
1. Write `shared/protocol/room-token.ts` holding the format and nothing else: header and
   claim shape, encode/decode, the `typ: "SVRT1"` and `v: 1` constants, TTL, and the claim
   validation currently duplicated in `verifyRoomToken`. It takes a signer:

   ```
   type TokenSigner = { sign(input: string): Promise<Uint8Array> | Uint8Array };
   mintRoomToken(claims, signer): Promise<string>
   verifyRoomToken(token, signer): Promise<RoomClaims | null>
   ```

   Two adapters justify the seam: `webcryptoSigner` for Convex, `nodeCryptoSigner` for
   socket-server and the dev route.

2. Preserve constant-time comparison. `verifyRoomToken` currently uses `timingSafeEqual`
   from `node:crypto`; the shared module must compare in constant time without assuming a
   Node builtin. Put the comparison behind the signer interface or implement a constant-time
   byte compare in the shared module and test it — do not fall back to `===` on strings.

3. Migrate the three call sites to the shared module. `socket-server` imports it with the
   `.js` extension per its ESM resolution. Convex must be checked against its bundler
   before the other two are touched — if the shared module does not resolve inside a Convex
   function, stop and report; that finding alone justifies the original three-copy decision
   and the plan closes.

4. Keep every behaviour identical: 5-minute TTL, `exp` in seconds, claim rejection on
   malformed subject, minimum 32-character secret, and the existing failure mode of
   returning `null` rather than throwing.

5. Update `CLAUDE.md`. The room-admission section describes the three implementations as
   the design; it must describe the module and its two adapters instead. Committing the
   code without this leaves the file lying about the architecture.
</tasks>
