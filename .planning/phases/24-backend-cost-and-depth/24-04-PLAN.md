<objective>Replace the full-scene broadcast with an element patch stream, so relay egress tracks what the teacher changed rather than how large the board has grown.</objective>

<context>
Every stroke re-broadcasts the whole scene to every student. Worse, `publishScene` attaches
`files` whenever the board holds any, so once one image or `/code` block exists, every
subsequent update carries the entire binary payload — up to `MAX_BOARD_FILES_BYTES`
(2 MB) per event, 20 times a second, to every student.

Estimated ~45 MB/s while drawing, ~120 GB per class at full drawing duty. Patches bring
that to ~0.6 MB/s. Assumptions: `.planning/BACKEND-OPTIMIZATION-DECISIONS.md`.

docs/11 already specifies the payload as "scene update representation selected during
implementation" and "Incremental/new scene state + `boardVersion`", and docs/21 requires
late join to receive a snapshot rather than a replay. This implements both. It does not
introduce a CRDT: the teacher remains the single writer and the relay remains the single
authority for room state.
</context>

<tasks>
1. Write `shared/board/scene-diff.ts` as a pure module, importable from the Next.js build
   and from socket-server (ESM, so socket-server imports it with the `.js` extension):

   - `diffScene(prev, next) -> BoardPatch | null` — `null` when nothing changed.
   - `applyPatch(scene, patch) -> Scene` — total, no mutation of the input.

   `BoardPatch` carries `upserts` (elements new or whose Excalidraw `version` increased),
   `deletedIds`, an optional `order` (the full ordered id list, present **only** when the
   z-order sequence changed), and an optional `appState` (present only when
   `viewBackgroundColor` changed). Element ids are ~20 bytes, so shipping `order` on a
   z-order change is still an order of magnitude below a full scene.

   Diff on `id` + `version`/`versionNonce`. Do not diff on serialized text — that
   reintroduces the cost this plan removes.

2. Handle files separately from elements. The patch carries `addedFiles` keyed by file id
   and nothing else; a file id already sent in this room is never re-sent. Hot state keeps
   the accumulated file map so `board:current` still serves a complete scene to a late
   joiner. Cap `addedFiles` with the existing `boundedJsonValue` helper against
   `MAX_BOARD_FILES_BYTES`.

3. Add `board:patch` to `shared/protocol/socket.ts` with a Zod schema:
   `{ v, sessionId, ts, baseVersion, boardVersion, upserts, deletedIds, order?, appState?, addedFiles? }`.
   Bound it the same way `boardUpdateSchema` is bounded. Bump
   `SOCKET_PROTOCOL_VERSION`.

4. Keep `board:update` as the full-scene path. It stops being the hot path and becomes the
   three rare cases: first publish after connect, republish after a rejected patch, and
   loading a prepared board or template. Deleting it would leave no way to recover from a
   diverged base.

5. Add `applyPatch` to `socket-server/src/board-hot-state.ts`. It rejects a patch whose
   `baseVersion` does not equal the stored version and returns a discriminated result
   rather than throwing. Hot state stays the authoritative full scene — this is what keeps
   `board:request-current` unchanged for late join and reconnect.

6. Register `board:patch` in `socket-server/src/protocol.ts` through `onAdmitted` from
   24-03: teacher role, board-update budget, ack. On a rejected base, ack
   `{ ok: false, code: "RESYNC_REQUIRED" }` and emit the matching `protocol:error`; the
   teacher client responds by publishing a full `board:update`. On success, broadcast the
   patch unchanged to the room.

7. Rewrite the teacher publish path in `components/board/board-canvas.tsx` and
   `components/board/use-board-sync.ts`:
   - Replace the `JSON.stringify(elements)` fingerprint in `onChange` and the second one
     in `flushPending` with an id→version map. Two full serializations per change
     disappear.
   - `flushPending` diffs against the last acknowledged scene and calls `publishPatch`;
     it falls back to `publishScene` on `RESYNC_REQUIRED` or when there is no acknowledged
     base yet.
   - Advance the acknowledged base only on a successful ack, so a dropped patch cannot
     silently desynchronise the next diff.

8. Rewrite the student apply path in `use-board-sync.ts`. On `board:patch`, apply it when
   `baseVersion` equals the local version; otherwise emit `board:request-current` exactly
   once, reusing the existing `resyncRequestedRef` guard. `board:current` and
   `board:update` keep their current behaviour.

9. Update the specs this changes: document the patch payload and the resync rule in
   `docs/11_REALTIME_SOCKET_PROTOCOL.md`, and add `RESYNC_REQUIRED` and
   `PROTOCOL_VERSION_MISMATCH` to `docs/28_ERROR_CODES.md` with their user-facing text in
   `lib/user-facing-errors.ts`. CLAUDE.md requires codes come from the documented set, so
   the docs land in the same commit as the code.

10. Handle the version bump. The relay rejects a mismatched `v` with
    `PROTOCOL_VERSION_MISMATCH`; the client surfaces a reload prompt rather than retrying.
    A hard bump is acceptable because both sides ship from this repo in one deploy and no
    production deployment is linked yet — record that reasoning in the protocol file so a
    future bump reconsiders it.
</tasks>
