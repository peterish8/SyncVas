<objective>Collapse the copied seven-step admission preamble into one interface, and close the two defects that the copying produced.</objective>

<context>
`socket-server/src/protocol.ts` is 262 lines for four handlers. Each repeats: `safeParse`
→ `getClaims` → `requireLiveClaims` → `getClaims` again → sessionId match → role check →
rate limit. Roughly 200 of the 262 lines are preamble around four lines of behaviour.

Two defects follow directly from that shape:

- `block:highlight` never calls `allowAction`. It is the one teacher event with no rate
  limit.
- `BOARD_UPDATE_MIN_MS` is 50 (20 updates/s) while `LIMITS.boardUpdatePerMinute` is 600
  (10/s). Sustained drawing exceeds the relay's own budget by 2× and earns
  `RATE_LIMITED` mid-lesson.

They are fixed here rather than as isolated patches because the seam is what prevents
the next one.

This plan changes no wire format and no payload schema. It runs before 24-04 so that
adding `board:patch` costs four lines.
</context>

<tasks>
1. Write `socket-server/src/admission.ts` exporting one interface:

   ```
   onAdmitted<S extends ZodTypeAny>(
     socket, event, schema,
     { role?: "teacher"; budget?: number },
     handler: (payload: z.infer<S>, claims: RoomClaims) => void,
   ): void
   ```

   It performs, in order: parse → resolve claims once → expiry → revoked → sessionId
   match → role → rate limit, emitting the existing `protocol:error` codes unchanged
   (`INVALID_PAYLOAD`, `UNAUTHORIZED`, `TOKEN_EXPIRED`, `ROOM_REVOKED`, `ROOM_MISMATCH`,
   `FORBIDDEN`, `STUDENT_BOARD_EDIT_FORBIDDEN`, `RATE_LIMITED`). The handler runs only
   with valid claims, so it cannot skip a step.

2. Resolve claims once. The current code calls `getClaims` before `requireLiveClaims` and
   again after it, purely to satisfy narrowing. `onAdmitted` resolves once and passes the
   claims in.

3. Keep the per-event acknowledgement contract. `board:update` alone takes a
   `BoardUpdateAck`; make the ack an optional part of the `onAdmitted` options so a
   rejection still acknowledges `{ ok: false, code }` for that event and stays silent for
   the others. Do not give every event an ack — the client does not expect one.

4. Rewrite the four handlers in `protocol.ts` on top of `onAdmitted`. Each keeps only its
   own behaviour: version check and hot-state write for `board:update`; scene serve for
   `board:request-current`; viewport store and volatile emit for `teacher:viewport`;
   volatile emit for `block:highlight`.

5. COST-04a — give `block:highlight` a budget. Add
   `LIMITS.blockHighlightPerMinute` to `socket-server/src/config.ts` and pass it. Set it
   from the teaching mechanic, not from a guess: highlights are a deliberate teacher
   action, so a low double-digit ceiling is right. Document the number's reasoning in the
   `LIMITS` comment, as the neighbouring entries do.

6. COST-04b — reconcile the cadence with the budget. `BOARD_UPDATE_MIN_MS = 50` implies
   1200 updates/minute against a 600 budget. Raise `boardUpdatePerMinute` to sit above the
   client's own ceiling with headroom for reconnect bursts, and add a comment stating the
   relationship so the two constants cannot drift again. Do not raise the client cadence.

   Note for 24-04: once patches replace full scenes the byte cost per event collapses, so
   this budget is about event volume, not bandwidth. Leave it framed that way.

7. Keep the `@phase` headers accurate and keep `debugEvents` gating unchanged — per-event
   logging stays opt-in behind `SOCKET_DEBUG_EVENTS=1`.
</tasks>
