Syncvas · architecture proposal

Prepared boards and live quizzes

Two features that look like new subsystems and are mostly reuse. The prepared board enters the room through the board path you already have; the quiz runs entirely on Convex reactivity and adds no socket events at all.

3 new tables 0 new socket events 1 locked decision to revisit Sept 2026

The shape of it

Where each feature actually lives

You already made the load-bearing decision — Convex is durable state, Socket.IO is the ephemeral pen path. Both features fall cleanly on one side or the other, which is why neither needs new transport.

Rides board:update

Prepared board → Socket path

A prepared scene is just a scene. The teacher's client loads it, pushes it into Excalidraw, and publishes it as board version 1. Students receive it through the same board:current bootstrap that already serves late joiners.

Student-side code changes: none.

Rides Convex reactivity

Quiz → Convex path

A reveal happens a handful of times per class, must survive a refresh, and must never expose the answer. That is durable low-frequency state — exactly what Convex is for, and exactly what Socket.IO is wrong for.

New socket events: none.

The one rule that keeps this cheap

Anything that happens more than a few times per second goes over the socket. Anything that must be durable, authorized, or secret goes through Convex. Neither of these features has a high-frequency component, so neither one earns new transport. That is the whole resource story.

Feature 1

Prepared boards

Author at home, walk in, start teaching.

A teacher builds a board the night before — diagrams drawn, questions placed, whitespace left where they intend to write live. In the morning they pick it from a library and the class opens on it.

Data model — one new table

// A template is owned by the teacher and reusable across sections.
// It is NOT a boardSnapshot: snapshots belong to one session,
// templates outlive sessions and get used many times.
boardTemplates: defineTable({
  teacherId:   v.id("users"),
  title:       v.string(),
  subject:     v.optional(v.string()),
  sceneJson:   v.string(),        // same validator as boardSnapshots
  blockSources: v.optional(v.string()), // grammar sources, for re-render
  origin:      v.union(v.literal("authored"), v.literal("ai-assisted")),
  createdAt:   v.number(),
  updatedAt:   v.number(),
}).index("by_teacher_updated", ["teacherId", "updatedAt"])
Why not reuse boardSnapshots

Tempting, because the scene shape and the 900 KB validator are identical. But boardSnapshots.sessionId is required and a template has no session — you would end up with a nullable foreign key and a kind union doing two unrelated jobs. That makes boardSnapshots shallower, not the codebase smaller. Separate table; share the validator, not the row.

AI assistance — the important call

✗ AI emits Excalidraw JSON

Megabytes of element objects with coordinates, seeds and version counters. Unreviewable, expensive per call, and a malformed field produces a corrupt scene that fails somewhere deep in the canvas.

✓ AI emits grammar source

A few hundred bytes of /mermaid, /ds, /code. Cheap, diffable, human-reviewable. Malformed output fails at your compiler with a clear message and never reaches the board. The teacher edits intent, not output.

// What the model returns — small, checkable, and yours to compile.
{ "blocks": [
    { "grammar": "mermaid", "source": "flowchart LR\n A[Input]-->B[Hidden]-->C[Output]" },
    { "grammar": "math",    "source": "\\sigma(x)=\\frac{1}{1+e^{-x}}" },
    { "grammar": "quiz",    "source": "Q: Which activation saturates?\n* sigmoid\n- relu" }
  ],
  "writingZones": 2 }
// Note what is absent: no x, no y, no width. Coordinates are never the model's job.
Layout is ours, not the model's

The model produces content and a count of writing zones. A deterministic layout function places the compiled blocks on a grid and reserves the requested whitespace by construction. Language models are bad at spatial arithmetic and good at content; asking for coordinates gets you overlapping boxes and no free space. Asking for content and doing the geometry yourself gets you a usable board every time.

Feature 2

Live quizzes

Two presentations, one data model, one answer path.

You described two experiences: blurred question cards on the board that students roam to find, and a locked full-screen final quiz. Modelling those as two subsystems would be a mistake — they are the same questions, the same answers, the same scoring, and the same leaderboard. Only the presentation differs, so presentation is a field.

quizQuestions: defineTable({
  sessionId:    v.id("sessions"),
  order:        v.number(),
  kind:         v.union(v.literal("mcq"), v.literal("truefalse")),
  presentation: v.union(v.literal("board"), v.literal("fullscreen")), // ← the only difference
  prompt:       v.string(),
  options:      v.array(v.string()),
  correctIndex: v.number(),        // NEVER leaves the server
  status:       v.union(v.literal("hidden"), v.literal("revealed"), v.literal("closed")),
  anchorX:      v.optional(v.number()),  // board mode: where the card sits
  anchorY:      v.optional(v.number()),
  revealedAt:   v.optional(v.number()),
}).index("by_session_order", ["sessionId", "order"])

The security model — get this wrong and the quiz is pointless

✗ Blur it on the board

Put the question and options into the scene, render them with a CSS blur, unblur on reveal. The scene is broadcast to every student, so the answer is already sitting in their browser. Any student opens devtools and reads it. Any student saves the scene.

A visual blur is not a security boundary.

✓ Withhold it on the server

The board carries only an anchor card — a placeholder element whose customData holds a question id and nothing else. Prompt and options are delivered by a Convex query that returns them only when status !== "hidden". correctIndex is never in any student-facing projection at all.

Grading happens inside the mutation.

// The student-facing projection. correctIndex is not in the return type,
// so it cannot leak by accident later.
export const listForStudent = query({
  args: { sessionId: v.id("sessions") },
  handler: async (ctx, args) => {
    const rows = await ctx.db.query("quizQuestions")
      .withIndex("by_session_order", q => q.eq("sessionId", args.sessionId))
      .collect();
    return rows.map((q) => q.status === "hidden"
      ? { questionId: q._id, order: q.order, status: q.status }        // anchor only
      : { questionId: q._id, order: q.order, status: q.status,
          kind: q.kind, prompt: q.prompt, options: q.options });       // no answer key
  },
});

Scoring — speed is part of the score

elapsed = clamp(answeredAt - revealedAt, 0, windowMs)
points  = isCorrect ? round(BASE * (1 - 0.5 * elapsed / windowMs)) : 0

// BASE 1000, windowMs 30_000.  Correct at t=0 → 1000.  At the window edge → 500.
// Wrong → 0 regardless of speed.  Rank by points, ties broken by total time.

The 50% floor is doing real work. Pure speed scoring rewards fast guessing, which is the wrong incentive in a classroom; correctness-only scoring makes the race pointless. Scaling down to a floor rewards the student who knows it cold while keeping a considered correct answer clearly worth more than a wrong fast one.

Why a scores table instead of deriving it

Deriving the leaderboard means scanning every answer on every read. With 100 students each holding a live leaderboard subscription, one answer invalidates 100 recomputes over a growing table. Patching one score row inside the same mutation that writes the answer is O(1), and the leaderboard becomes an indexed descending read of the top N. This is the one place denormalisation earns its keep, because both writes happen in the same transaction and cannot drift.

Locked mode

// One field on sessions drives the whole locked experience.
roomMode: v.union(v.literal("board"), v.literal("quiz-locked"))

The student shell already subscribes to session state. When roomMode flips, it swaps the board for the full-screen quiz and stops rendering canvas controls. Because it lives in Convex rather than in a socket event, a student who refreshes mid-quiz lands back in the quiz instead of on a stale board — which is the actual failure you would hit with an ephemeral signal.

Decision to revisit

A leaderboard conflicts with a locked decision

Contradicts PROJECT.md

"Anonymous student join; doubts anonymous in teacher UI; pseudonymous participant IDs backend" is marked ✓ Locked. A leaderboard of SHA-256 hashes is neither fun nor legible, so this feature cannot ship without reopening that decision.

The resolution keeps the part that matters. Anonymity exists in this product to protect shy students asking questions — that is what the doubts loop is for, and it should not change. A quiz leaderboard is a different social contract, and students opting into a game is not the same as students being identified when they admit confusion.

Decided: students type their own display name at join. It passes through deterministicScreen() in convex/moderation.ts before storage, so the profanity and noise rules you already wrote cover it. The name is used on quiz leaderboards and nowhere else — the doubts queue still shows nothing.

What stays true

  • No accounts, no login, no email
  • Doubts carry no name — the protection that mattered is intact
  • Backend identity is still the pseudonymous participant hash
  • Names are screened by code you already wrote

What changes

  • participants gains a displayName field
  • Join gains a name field; PROJECT.md gains a scoped amendment, not a reversal
  • Leaderboards show names, never hashes
Accepted risk

Self-chosen names allow impersonation — a student can type a classmate's name, or the teacher's. Screening catches profanity, not identity theft. Give the teacher a way to rename or remove a participant from the leaderboard, and treat that as the mitigation rather than trying to prevent it at entry.

Scope

Where this belongs

You asked for v1. Here is the honest arithmetic, and then a way to get you what you actually want.

v1.0 is P0+P1 across ten phases, and phases 3–10 are still implementation-complete-but-UAT-pending. Adding a quiz subsystem and a template library to it does not accelerate anything; it moves the finish line while the current one is unverified.

But there is a real dependency that settles the question. AI-assisted prepared boards need the block grammars from v1.1 — that is what makes AI generation cheap, checkable and safe. Prepared boards and grammars are not two milestones competing for position; they are one feature and its enabling layer.

Decided — these are v1.0

They ship in v1.0 as phases 11–15, gated behind P1 (phases 7–9) being verified. Board Grammars moves to phases 16–20.

That creates one dependency to resolve: AI authoring was going to lean on the block grammars. Scoping v1.0's AI output to mermaid only breaks that link — mermaid-to-excalidraw is a standalone MIT library that needs no block primitive — so phase 12 does not wait on phase 16. Richer grammars in generated boards arrive with v1.1.

Before planning

Open questions

Does a late joiner get to answer already-revealed questions?

Affects fairness and the leaderboard. Recommendation: no — a question closes for scoring when the teacher closes it, and a student who joins after reveal can see it but scores zero. Simple, explainable to a room, and needs no retroactive grading.

Is speed part of the score? — Decided: yes, directly

Speed scales the points for a correct answer, it is not just a tiebreak. Correct answers run from 1000 down to a floor of 500 across the question window; wrong answers score zero however fast they arrive. The floor is what stops it becoming a guessing race. See the scoring formula above.

Can a teacher reuse a quiz across sections, like a board template?

Very likely yes, and it is the same shape as boardTemplates. Worth deciding before phase 16 so questions are authored into a reusable set from the start rather than migrated later.

What happens to an in-flight quiz when the class ends?

sessions.end already refuses to finalise without a snapshot. Quiz state should close open questions and freeze the leaderboard into the ended session, so history shows both the final board and the final scores.
